# yanua-local-ai

社内の資料に答える、外部にデータを出さないローカルAIです。

社内規程・マニュアル・ナレッジを読み込み、出典つきで答えます。LLMは Ollama で社内のマシン上に置き、質問・資料・回答を社外に送りません。

- **社内向け**：社員の質問への回答と、システムの問い合わせに対応するヘルプデスク（本人確認 → 切り分け → 案内 → 引き継ぎの票）。総務の作業として、紙の書類をPDFにしたあとの仕分けと Word・Excel への変換、会議の録画・録音からの議事録づくり。
- **社外向け**：電話・Webの問い合わせと来訪を受ける受付（問い合わせへの回答、社員への取次、クレーム、営業・業者の対応）。社外に公開してよい文書だけを使います。

前身は [ai-callcenter-ollama](https://github.com/mismd2026/ai-callcenter-ollama)（電話で応答するAI）です。その受け答えの仕組みを、社内の資料と権限の上に作り直しています。

## 目指す動き

- **出典つきで答える。** 回答に、元になった文書名と該当箇所を付けます。
- **資料にないことは答えない。** 根拠が見つからない質問には、推測せずに「わかりません」と答えます。
- **部署ごとの閲覧権限を守る。** 見る権限のない部署の資料は、検索の段階で除きます。
- **通信は限定して、安全に。** 質問・資料・会議の中身は社外に送りません。通信するのは、モデルの入手のように管理者が実行するときだけで、相手は許可リストの宛先に限ります（下の「通信の方針」）。

## 使い方

Python 3.11 以上で動きます。

```bash
pip install -r requirements.txt
```

```bash
# 資料を取り込む。2回目以降は、変わった文書だけを反映し、なくなった文書は消す
python -m yanua ingest demo/company/docs

# 部署の権限つきで検索する
python -m yanua search "在宅勤務は週に何日までできますか？" --department 営業部

# 取り込んだ文書と、閲覧できる部署の一覧
python -m yanua docs

# Ollamaで出典つきの回答を作る（Ollamaが動いていること）
python -m yanua ask "在宅勤務は週に何日までできますか？" --department 営業部 --model qwen2.5:3b-instruct

# Web画面・クライアントアプリ向けの API を起動する（開発用ログインつき。API の一覧は http://127.0.0.1:8000/api/docs）
python -m yanua serve --dev-login --model qwen2.5:3b-instruct --port 8000
```

### API（yanua/api）

画面の一覧・API の一覧・共通の決まりは [docs/screens.md](docs/screens.md) にあります。今あるのは段階1（ログイン・権限・ジョブ・質問・検索・文書・ヘルプデスクの会話）です。

- **ログイン**：今は開発用ログイン（`--dev-login`、社員番号を送る）だけで、127.0.0.1 で待ち受けるときしか使えません。本番の SSO は K-008 で作ります。毎回のリクエストで人事データを引き直すので、退職した人はその時点で使えなくなります。
- **権限**：考え方は [docs/access-model.md](docs/access-model.md)（役割 × 対象 × グループ）。下の「権限の仕組み」の節
- **部署**：質問・検索で見てよい文書は、ログインした人の権限（documents.view が効く部署。ふつうは自分の部署）で決めます。リクエストの本文で部署を渡しても使いません。
- **CSRF 対策**：GET 以外のリクエストには `X-Yanua-Client` ヘッダーが必要です。
- **ジョブ**：取り込みのような重い処理はジョブで受け付けます（`202` とジョブの番号を返す）。同時に流すのは1つずつです。
- **会話**：ヘルプデスクの会話の途中の状態は `data/chat.db` に残すので、サーバーを再起動しても続けられます。30分返事がない会話は消えます。

```bash
curl -c c.txt -H 'X-Yanua-Client: curl' -H 'Content-Type: application/json' \
     -d '{"employee_no": "10004"}' http://127.0.0.1:8000/api/auth/dev-login
curl -b c.txt -H 'X-Yanua-Client: curl' -H 'Content-Type: application/json' \
     -d '{"question": "在宅勤務は週に何日までできますか？"}' http://127.0.0.1:8000/api/ask
```

段階2の API（画面は次の段階）：

- **お知らせ**（`GET /api/notifications`・`POST /api/notifications/read`）：自分あてと、自分の部署あてだけ。ほかの人のお知らせの番号を送っても既読になりません
- **来訪予定**（`POST・GET・DELETE /api/visits`、`POST /api/visits/import`）：社員は自分が担当の予定だけ。総務は全社の予定（`?date=`）・ほかの人の予定の登録と取り消し・CSV の取り込み（本文に CSV をそのまま送る。カレンダーの書き出しも同じ API）。インビテーションコードは登録したときに1回だけ返します
- **受付の記録**（`GET /api/reception/records`、`POST .../{id}/done`）：総務だけ
- **問い合わせ票**（`GET /api/tickets`・`GET/PATCH /api/tickets/{id}`）：情シスだけ。状態は 未対応・対応中・対応済み
- **受付端末**：管理者が `POST /api/admin/kiosk-devices` で端末を登録すると、端末トークンを1回だけ返します。受付端末は `Authorization: Bearer <端末トークン>` で `/api/kiosk/sessions`・`/api/kiosk/check-in` だけを使えます（`/api/kiosk/...` は端末トークン専用）。違う日・間違い・取り消しのコードには、同じ形・同じ時間で返事をします。入館票は受付端末の画面が返事から作って印刷します

段階3の API（画面は次の段階）：

- **ファイルの受け渡し**：`POST /api/uploads?kind=pdf|recording|segments&name=...` に本文でファイルを送ります（上限：PDF 50MB・録画 2GB）。結果のファイルは `GET /api/files/{file_id}` で受け取ります。開けるのは作った本人で、その種類の権限がある人だけです。アップロードも結果も24時間で消えます。作業用フォルダ（既定 `data/work`）の合計にも上限（`work_max_bytes`、既定 20GB）があり、超えるアップロードは断ります（507）
- **PDF の仕分け**（総務）：受信箱（既定 `demo/company/paper/inbox`）の一覧 → `POST /api/paper/plans` で予定を作る（ジョブ）→ `PUT /api/paper/plans/{id}/items/{index}` でルールを選び直す → `POST .../execute` で保存先（既定 `data/paper/sorted`）に置く → `GET /api/paper/history` で記録。予定は作った人だけが見られますが、仕分けの記録は総務の全員が見られます。未分類の PDF からは、画面でルールの下書きを作って直し、検証してから保存できます（`POST /api/paper/rule-drafts`・`POST /api/paper/rules`）。保存したルールは `data/settings/rules.json` に全部の写しとして書き、既定の `rules.json` は書き換えません（「画面で変えた設定」）。保存の前の版は残り、`POST /api/paper/rules/history/{版}/restore` で戻せます。`POST /api/paper/rules/reset` で既定に戻せます
- **PDF の変換**（総務）：`POST /api/paper/convert`（ジョブ）。アップロードした PDF か受信箱の PDF を、Word・Excel にします。`form: true` なら仕分けルールの会社の様式に差し込みます
- **議事録**（社員。自分のものだけ）：録画をアップロード → `POST /api/meetings`（ジョブ：文字起こし → 話し手 → 要約）→ `GET/PUT /api/meetings/{id}` で確認と修正（「不明」の話し手を直す、要約・宿題を直す）→ `GET /api/meetings/{id}/minutes.docx`。文字起こしのモデル（`models pull whisper-small`）がないときは、文字起こし済みの発言（`kind=segments`。デモは `demo/company/meeting/demo_zoom_segments.json`）を一緒に渡せば試せます

前の API（`POST /ask` だけ）は `python -m yanua serve-legacy` で起動できます。

### Web画面（web/）

段階1の画面（S-01 ログイン・S-02 ホーム・S-03 ジョブ・S-10 チャット）があります。Node.js 20.19 以上で組み立てます。組み立てるときだけ npm からライブラリを入手し、動かすときは社外と通信しません。

```bash
cd web
npm ci            # ライブラリを入れる（版は package-lock.json で固定）
npm test          # 画面のテスト（偽の API で確かめる。サーバーも Ollama も使わない）
npm run build     # 組み立てる → web/dist
cd ..
python -m yanua serve --dev-login   # http://127.0.0.1:8000/ で画面が開く
```

受付端末を試すには、先に管理者（例：社員番号 `10005`）で端末を登録して、端末トークンを受け取ります（登録の画面は次の PR 以降。今は http://127.0.0.1:8000/api/docs の `POST /api/admin/kiosk-devices` に `{"name": "受付1"}` を送ります）。タブレットのブラウザで http://<サーバー>/kiosk を開き、最初の設定の画面に端末トークンを入れます。トークンはその端末のブラウザにだけ残ります。**受付端末では社内にログインしないでください。** 受付端末の画面は、開くたびと端末トークンを設定するときに、そのブラウザの社内のログインを消します（来訪者が社内の画面を開けないようにするため）。

画面を直しながら試すときは、API を `serve --dev-login` で動かしたまま、`cd web && npm run dev` で http://127.0.0.1:5173/ を開きます（/api は 8000 番に渡します）。

- **ログイン（S-01）**：開発用ログインのときは社員番号を入れます。SSO（K-008）はまだです
- **ホーム（S-02）**：使える画面のメニュー（`/api/me` の permissions で出し分け）、実行中のジョブ。お知らせの件数は、お知らせの API（段階2）ができたら出ます
- **チャット（S-10）**：「社内文書に質問」は出典つきの回答です。待っている間は進み具合だけを出し（`POST /api/ask/stream`）、回答の文はルールで確かめ終わってから出します。出典を押すと文書のその節を横に開きます（`GET /api/documents/{doc_id}`。見られる文書だけ）。「ヘルプデスクに相談」は本人確認を省いてお困りごとから始め、解決しなければ問い合わせ票の番号を出します
- **ジョブ（S-03）**：自分のジョブの状態・進み具合・始めた時刻、詳しい内容（結果・エラー）、取り消し。管理者は「すべての人のジョブ」に切り替えられ、文書の取り込みをここから始められます（取り込めるのは設定の `ingest_roots` とその直下のフォルダだけ。既定は `demo/company/docs` と `demo/company/public`）。実行中のジョブがあるあいだだけ3秒ごとに更新します
- **段階2の社内の画面**：お知らせ（S-11）、自分の来訪予定（S-12。登録するとコードと案内文をその場で1回だけ出す）、全社の来訪予定（S-22。総務。日付ごとの一覧と CSV・カレンダーの書き出しの取り込み）、受付の記録（S-23。総務）、問い合わせ票（S-30。情シス）。メニューは役割に応じて出し分け、ホームに未読のお知らせの件数を出します
- **段階3の社内の画面**：議事録（S-13。社員。録画を送る→進み具合→話し手・要約・決まったこと・宿題を直す→Word で出す。話し手が「不明」の発言は選んでまとめて直せる。自分の議事録だけが出る）、PDF の仕分け（S-20。総務。受信箱→予定を作る→ルールを選び直す→確かめてから実行→記録。記録は総務の全員が見られる）、PDF の変換（S-21。総務。送った PDF か受信箱の PDF を Word・Excel・会社の様式にしてダウンロード）。録画は送った量を進み具合で出します
- **受付端末（/kiosk）**：S-40 受付（「コードをお持ちの方」「お持ちでない方」→ コードの入力、または用件の会話）と S-41 予定の表示と入館票の印刷。社内の画面とは別に組み立て（`kiosk.html`）、メニューもリンクも置きません。60秒触られなければ最初の画面に戻ります
- 画面でボタンを隠すのは使いやすさのためです。権限は API の側で確かめます

### 回答

- 検索で見つかった本文だけを番号つきでLLMに渡し、その範囲だけで答えさせます。回答の [1] などの番号から出典を決めます。
- 資料に根拠がないときは、推測せずに「わかりません」と答え、問い合わせを案内します。
- LLMに渡すのは、質問者が見られる文書の本文だけです。LLMがどう答えても、見られない文書の内容は回答に出てきません。

取り込んだ内容は `data/index.db`（SQLite）に保存します。

### 取り込み

- 1文書1ファイルのMarkdownを、見出しごとに分けて登録します。
- ファイルの内容のハッシュを比べ、変わった文書だけを登録し直します。
- 取り込むのは、コマンド（`python -m yanua ingest <フォルダ>`）か、画面「文書」（S-50）・「ジョブ」からです。画面から取り込めるのは、設定の `ingest_roots`（既定は `demo/company/docs` と `demo/company/public`）の下のフォルダだけです。どちらもジョブ（`ingest`）で、同じフォルダから前に取り込んで今はない文書は消します。
- **公開先の決め方**：初めて取り込んだときに、次のどちらかで決めます。
  - ファイルの先頭の `owner`（持ち主の部署）と `access`（部署・`全社`・`社外公開`）。`access` がない文書は取り込みません（書き忘れた文書が全員に見えてしまうのを防ぐため）
  - 画面「文書」で選んだ、持ち主の部署・公開先・見るのに要る権限（新しく足す文書だけに使います）
- 取り込み直したとき、ファイルの先頭で決めた文書は、ファイルの `access` に合わせ直します。画面で決めた・直した文書は、画面のものを残します。

### 文書の公開先と、見るのに要る権限（S-50）

考え方は [docs/access-model.md](docs/access-model.md) です。

- 文書は、**持ち主の部署**・**公開先**（部署・グループ・全社から1つ以上）・**見るのに要る権限**（既定は `documents.view`。ほかに選べるのは、文書向けの `infra.docs.view`）を持ちます
- **見られるのは、見るのに要る権限を、公開先を含む対象で持っている人だけ**です。判定は `yanua/access.py`（`can`）で、文書の一覧・開く・検索・質問・ヘルプデスクの文書の検索（LLM に渡す前）は、すべてこれを通ります
  - 公開先「全社」は、どの対象にも含まれます（要る権限をどこかに持っていれば見られる）
  - ふつうの社員は「社員」の役割（documents.view × メンバー自身の所属（部署と、入っているグループ））なので、自分の部署・自分が入っているグループ・全社の文書が見られます
  - グループ専用の文書にするときは、公開先をそのグループにするだけで、そのグループの人が見られます。要る権限を infra.docs.view にしたときは、そのグループに infra.docs.view × そのグループ（か メンバー自身の所属）を与えます（画面 S-54）
  - 前の版のデータでは「社員」の対象が「メンバー自身の部署」（グループを含まない）でした。起動のときに1回だけ、自動で置き換えます（監査ログに残します）
- 見られない文書は、検索の候補にも入りません。題名も返事に出しません。権限で見せなかった文書の件数だけを、監査ログに残します
- ログインしない使い方（コマンドの `search --department`・本人確認で照合したヘルプデスク）は、その部署の社員と同じ範囲（documents.view × その部署と全社）です。照合できなかった人は全社の文書だけです
- 前の書き方からの移し替え：公開先＝前の `access` の部署（`全社` は全社）。`社外公開` の文書は、公開先「全社」と「社外公開」の印にします（社内では前と同じく全員が読め、社外向けの受付はこの印の文書**だけ**を使います）
- 画面「文書」（`/admin/documents`。`documents.manage` を持つ人）では、扱える部署（documents.manage の対象。持ち主の部署で決まる）の文書について、次のことができます
  - 公開先・要る権限・社外公開を直す（中身は変えません。検索の単位も作り直しません。すぐ検索に効きます）
  - 外す（検索にも一覧にも出さない）・「外したもの」から戻す
  - 変える前に、見られるようになる人・見られなくなる人を、グループごとの人数で確かめる（試しに当てるだけで保存しない）
- 変更・取り込み・外す・戻すは、監査ログに中身つきで残します（例：「就業規則（抜粋）の公開先 全社→経理部」）。文書の本文は残しません
- 同じ文書を取り込み直したときの前の版は残しません（課題 K-055）

### 検索の前の絞り込み

- 検索の前に、質問者が見られる文書だけをSQLで取り出し、その中だけを検索します（上の「公開先」の決まり）。
- LLMへの指示や、検索した後での除外には頼りません。見られない文書は、検索の候補にも入りません。
- 社外公開の文書は社外の人にも見せてよい文書です。社外向けの流れは、この文書**だけ**を検索します。

### 検索

- BM25で検索します。日本語は2文字ずつの組（バイグラム）で比べるので、辞書やモデルのダウンロードはいりません。
- 「夏休み」と「夏季休暇」のような言い換えには弱いため、埋め込みベクトルでの検索を後で組み合わせる予定です。

## 社内向けヘルプデスク

```bash
# 人事データを取り込む（本人確認に使う。下の「人事データの取り込み」を参照）
python -m yanua hr-import demo/company/hr/hr_export_sample.csv --mapping demo/company/hr/mapping_sample.json

# デモ（1：代表アカウント・プリンター、2：障害中、3：不審なメール、4：パスワード忘れ）
python -m yanua helpdesk --demo 1 --model qwen2.5:3b-instruct

# 対話（--account はログイン中のアカウント。SSOの代わり）
python -m yanua helpdesk --account yamada.t --model qwen2.5:3b-instruct
```

流れ：本人確認 → お困りごと → 分類 → 状況の聞き返し（2回まで）→ 障害の確認 → 案内 → 解決の確認 → 解決しなければ問い合わせ票

- **本人確認**（`yanua/identity.py`）：画面からログインしている人は省きます。個人アカウントなら、人事データの本人かどうかを確認するだけです。代表アカウントや、個人アカウントを別の人が使っている場合は、次のようにします。
  - **何で相手を特定するかは、本人確認の方針（`config/identity.json`）で決めます。** 社員コードを極秘にしている会社もあるので、型を用意しています。

    | 型 | 最初の聞き方 | 確定する組み合わせ |
    |---|---|---|
    | 標準（既定） | 所属部署とお名前と従業員番号 | 3つのうち2つ |
    | 相手に委ねる | お名前、所属部署、または従業員番号 | 3つのうち2つ（足りないものを後から聞く） |
    | 社員コードを使わない | お名前と所属部署（部署名か部署コード） | 名前＋部署 |
    | 社員コード必須 | 従業員番号とお名前 | 番号＋名前、番号＋部署 |

    型を選んだうえで、聞き方・使う手がかり・組み合わせ・聞き返しの回数を上書きできます。設定画面（K-042）から変えられるようにする予定です。
  - 返事は順番を問わず、ルールで手がかりを取り出します（「総務」は総務部、部署コードも部署として読む、全角の数字も読む）。
  - **名前は、フルネームが合ったときだけ手がかりに数えます。** 姓だけのときは数えず、番号などを求めます（マイク越しでは名前を聞き間違えやすいため）。数えるようにもできます（`surname_counts`）。
  - **確定しなければ、返ってきた言葉に合わせて聞き返します。** 部署だけなら「お名前か従業員番号」、名前がヒットしなければ「従業員番号」、姓だけなら「お名前（フルネーム）」。聞き返しは方針の回数（既定2回）までです。
  - 確定しなくても依頼は受けます。言われた内容（`declared`）と照合の結果（`matched`・`note`）は、照合できてもできなくても票に残します。候補になった人の名前や部署は、相手に見せません。
  - 言い方のパターンは網羅しません。実際の記録で「確定できなかった会話」を見て、多いものからルールに足します。
- **権限**：照合できた人は、その部署の権限で社内文書を検索します。照合できない人は「全社」の文書だけを使います。
- **案内**：まず社内文書から出典つきで答え、見つからなければ一般的な切り分けの手順で補います。
- **障害**：発生中の障害に当たる問い合わせは、個別の手順を案内せずに障害中であることを伝えます。
- **セキュリティ**：不審なメールなどは、検索の出来に関係なく決まったルールで拾い、聞き返しより先に「ネットワークから切り離す」案内を出して、必ず引き継ぎます。
- **優先度**：本人に聞かず、影響の範囲 × 業務への影響 から決めます。

LLM（3bなどの小さなモデル）の判断をそのまま使わず、結果が業務に響く判断（本人確認、セキュリティ、影響の範囲）は、決まったルールで固めています。
会話の流れの管理には LangGraph を使い、返事を待つところで処理を止めて再開します。

```bash
python -m yanua ingest demo/company/public

# デモ（1：インビテーションコードで来訪、2：電話の問い合わせ、3：Webのクレーム、4：お約束のない営業、

```

流れ：（来訪）インビテーションコード → ご用件 → 種類の判定 → 種類ごとの対応 → 社内向けの記録（受付番号、引き継ぎ先、優先度）と、担当者へのお知らせ

### インビテーションコード

アポを取ったときに担当者がコードを作って訪問者に送り、訪問者は受付でコードを入力します。受付は挨拶とコードの入力のお願いだけで済みます。

```bash
# 担当者：来訪予定を登録する。訪問者に送る案内文（日時・会議室・担当・コード）が出る
python -m yanua visit-create --host 10004 --date 2026-11-20 --time 14:00 --room "5階 第2会議室" \
    --company ABC商事 --visitor "木村 誠" --contact 内線4100

# 予定の一覧（コードは表示しない）と、担当者へのお知らせ
python -m yanua visit-list --date 2026-11-20
python -m yanua notifications --employee 10004 --dept 営業部 --mark-read
```

- 受付でコードが入力されると、日時・会議室・担当者・連絡先を表示し、印刷用の入館票（`data/passes/` のHTML）を作って、担当者にお知らせを残します。
- コードは紛らわしい文字を除いた8文字で、保存するのはハッシュだけです。コードを表示するのは、登録したときの1回だけです。入館票にもコードは載せません。
- 使えるのは予定の当日だけです。違う日のコードも、間違ったコードも、取り消したコードも、同じ「確認できませんでした」にします（どのコードが存在するかを探れないようにするため）。3回で、ご用件を聞く流れに移ります。
- コードを持っていない来訪者も、名乗りと当日の予定（会社名と担当者）で照合します。「ABC商事の木村です」のように名乗った場合は、聞き直さずに確認だけします。
- 担当者として登録できるのは、人事データで在籍中の人だけです。
- お知らせは今は保存先に残すだけです。メールやチャットへの送信は、`yanua/visits.py` の `notify` につなぎます。
- **Googleカレンダーからも発行できます。** 予定に会議室と社外のゲストを入れて保存すると、アドオン（Apps Script）でゲストごとにコードを発行してメールで送ります。シートに残すのはハッシュだけで、Yanua にはCSVで取り込みます（`visit-import`）。リスケや取り消しも反映します。入れ方は [integrations/google-calendar/README.md](integrations/google-calendar/README.md) を見てください。

| 種類 | 対応 | LLM |
|---|---|---|
| 問い合わせ | 社外公開の文書から出典つきで答える。答えられなければ連絡先を聞いて記録 | 使う |
| 取次（社員への用事） | 会社名・お名前と訪ね先を聞き、人事データで社員を探す。来訪予定と合えば会議室へ案内。電話・Webは折り返しの連絡先を聞く | 使わない |
| クレーム | 決まったおわびの文で内容と連絡先を聞き、お客様相談室へ（優先度：高） | 使わない |
| 営業 | お約束のない営業は、決まった文でお断りして資料を預かる | 使わない |
| 業者（納品・工事など） | 作業の内容を聞いて総務部へ | 使わない |

社外の人と話すので、社内向けより守りを固くしています。

- **文書**：答えに使うのは社外公開の文書だけです。人事評価のような部署限定の文書も、全従業員向けの文書も、LLMに渡りません。「人事評価の基準を教えて」のような質問には、答えずに担当部署からの連絡にします。
- **社員の情報**：訪ね先の社員は人事データ（在籍中の人）から探しますが、所属・連絡先・在籍しているかどうかは返事に出しません。退職した人やいない人を訪ねられても、在籍中の人と同じ返事・同じ質問の流れにして、総務部が確認します。同じ姓の社員が複数いるときも聞き直さず、候補を記録に残して総務部が確認します（聞き直すと、その姓の社員が複数いることが分かってしまうため）。「山田様に用が」のように人を名指しした用件は、社員かどうかにかかわらず取次として扱います。
- **LLMに作らせない文**：クレームのおわびや、営業へのお断りは、`routes.csv` の決まった文だけを使います。できない約束をしないためです。
- **言い方**：お客様の言葉をそのまま返して「御社の営業時間は」とならないよう、答えの「御社」「貴社」は「当社」に直します。
- **記録とお知らせ**：解決した問い合わせも記録します（よく聞かれる内容を集計するため。お知らせは出しません）。解決しなかったものは、引き継ぎ先の担当者か部署にお知らせを残します。
- **種類の判定**：決まった言葉で判定し（クレームを最優先）、当たらないときだけLLMに選ばせます。選択肢以外の返事は「問い合わせ」として扱います。

## 人事データの取り込み

人事DBには直接つながず、人事システムから出力したファイル（CSV / Excel / JSON）を取り込みます。ふだんは画面（S-51「人事データ」、`/admin/hr`。`hr.import` を持つ人）で取り込みます。コマンドでも取り込めます（画面と同じ処理を通ります）。

```bash
# 列名から対応表の下書きを作る（列名と在籍状態の列の値だけを使う）
python -m yanua hr-mapping-draft 人事出力.xlsx

# 下書きを確認して保存した対応表で取り込む（監査ログに「サーバーの操作」で残す）
python -m yanua hr-import 人事出力.xlsx --mapping 対応表.json                 # 一部のファイル（既定）
python -m yanua hr-import 人事出力.xlsx --mapping 対応表.json --scope all     # 全員のファイル
```

**デモの人事データを、前の作りで取り込んでいたとき**：前の作りは在籍と休職を分けていなかったので、10006（伊藤 直子、人事部）は「在籍」になっています。デモの CSV を今の作りで取り込み直すと、CSV のとおり「休職」に変わります（意図どおりです。試しの結果に「在籍状態 在籍→休職」と出ます）。休職中の人の扱いの既定は「ログインできる・権限そのまま」なので、取り込み直しても 10006 のログインと権限は変わりません。

- **読むのは、割り当てた列だけ**です：社員番号・氏名・よみ・部署名・部署コード・在籍状態・メールアドレス・雇用区分・期限・役職・役職の段。住所・給与・生年月日などの列がファイルにあっても、その列の値は読みません（`yanua/hrimport.py`。持つ項目・持たない項目は docs/access-model.md の「人の台帳」）
- **列の対応づけ**：人事アプリごとに列名が違うので、画面でファイルの列を Yanua の項目に割り当てます。名前を付けて保存すると、次から選べます（既定は `config/hr_mappings.json`、画面で保存したものは `data/settings/hr_mappings.json`。版が残ります）。決まったルールで当たらない列だけ、コマンドの `--use-llm` で Ollama に候補を聞けます（渡すのは列名だけ）
- **在籍状態**：ファイルの値（例「在職」「休業」「退社」）を、Yanua の3つ（在籍・休職・退職）に当てます（対応表の `status_values`）。当てていない値は誤りです。前の書き方の `active_values`（在籍とみなす値）も読めます（その値は在籍、「休職」は休職、ほかは退職）
- **雇用区分・期限・役職・役職の段**（人の属性。権限は持ちません）：雇用区分は、ファイルの値（例「正社員」「契約社員」「業務委託」）を5つ（社員・契約・派遣・短期・外部委託）に当てます（対応表の `employment_values`。在籍状態と同じ作り）。期限は契約の終わりの日（`2027-03-31` か `2027/03/31`。空なら期限なし）、役職の段は比べるための数（1〜99）です。読めない値は行番号つきの誤りです。この版より前からいる人は「社員」・期限なし・役職は空です。役職の段は、段で決まるグループ（既定の「経営」など）を通して権限に効きます
- **取り込みの種類**：「一部のファイル」（既定。ファイルにいない人は変えない。例：営業部だけのファイル）と「全員のファイル」（ファイルにいない人は、いなくなる人として消す）から選びます。選んだ種類は、試しの結果・記録・監査ログに出ます。全員のファイルで、いなくなる人が今の人数の 10% を超えるときは「いなくなる人が N人（全体の M%）います」と出し、もう一度押したときだけ確定します（コマンドは `--confirm-removal`）。1つ前に戻すのは、控え（全員のデータ）を入れるので、全員のファイルと同じ扱いです
- **「使わない」にした列**：任意の列（よみ・部署コード・メールアドレス・在籍状態・雇用区分・期限・役職・役職の段）を使わないにすると、今いる人のその列の値をそのまま残し、「変わる人」にも数えません。新しく入る人だけ、その列が空（在籍状態は「在籍」、雇用区分は「社員」）で入ります
- **試してから確定**：画面では、まず「試す」（保存しない）で、新しく入る人・変わる人（部署・在籍状態・名前など）・いなくなる人の件数と先頭の数件、「権限への効き方」（入る人・部署や在籍状態や役職の段が変わる人・いなくなる人の、入るグループ・外れるグループ。グループごとの人数）を出します。誤り（社員番号の重複・必要な列がない・空の欄・知らない在籍状態）は行番号つきで出し、誤りが1件でもあれば確定できません
- **確定**は、まとめて1回で入れ替えます（途中で失敗したら前のまま）。そのあと、部署の一覧と権限の結果を作り直します。確定すると roles.assign を持つ人がいなくなるときは、確定しません
- **前の取り込みに戻す**：直近3回分の前のデータを残し、「1つ前に戻す」で戻せます（戻す前にも試しの結果を出します。戻ってくる人・いなくなる人の入るグループ・外れるグループも、取り込みの試しと同じ数え方で出します。戻したことも、また戻せます）。記録の名前は「元のファイル名（戻した）」で、何回戻しても「（戻した）」は1つだけです。手で入れたグループのメンバーは、戻しても戻りません
- **退職・休職**（docs/access-model.md）：退職した人はログインできず、本人確認でも一致しません。手で入れたグループのメンバーとしても数えず、取り込みのときに外します（監査ログに残します。在籍に戻っても自動では戻しません）。休職中の人は本人確認では一致します。ログインと権限は設定（S-52 の「人事」）で選べます。既定は今のまま（ログインできる・権限そのまま）
- **一覧**（画面の「一覧」。`hr.view` を持つ人）：社員番号・氏名・部署・在籍状態・最後に変わった日だけを出します。見られるのは hr.view の対象の部署の人だけです
- 監査ログには、件数と変わった人の社員番号だけを残します（氏名やメールアドレスは入れません）
- 人事データや対応づけに誤りがあっても、**起動は止めません**（今の人事データのまま動き、画面の上に理由を出します）
- 照合用に、正規化した氏名・姓・部署の列と索引を作ります。在籍者を全部読まずに名前や部署から引けるので、100万人のデータでも照合は1回数ミリ秒です（`python eval/bench_identity.py --employees 1000000`）
- **大きさ**：100万人のファイル（CSV 128MB）で、試し約11〜14秒、確定約22〜30秒、一部のファイル（1つの部署の1,000人）の試し約5秒、1つ前に戻すのは試し約3秒・確定約19秒でした（`python eval/bench_hr_import.py --employees 1000000`。8コア・メモリ 8GB の WSL2。保存先は控え3回分を入れて約550MB）
- 最後に取り込んでから30日を過ぎると、ヘルプデスクの起動時に警告します

## 紙の書類のPDF（仕分けと変換）

複合機でスキャンしたPDFを、ルールに沿って名前を付け、決まったフォルダへ仕分けます。PDFを Word や Excel にも変換できます。
文字の入っていないPDF（画像だけのスキャン）は、この端末の中で OCR（tesseract）して読みます。社外には送りません。

```bash
# OCRの準備（WSL / Ubuntu。文字の入ったPDFだけなら不要）
sudo apt install tesseract-ocr tesseract-ocr-jpn poppler-utils

# ルールの一覧と、仕分けの予定（--dry-run では置かない）
python -m yanua pdf-rules --rules demo/company/paper/rules.json
python -m yanua pdf-sort demo/company/paper/inbox --rules demo/company/paper/rules.json --out 仕分け済み --dry-run

# 仕分ける（既定はコピー。--move で移す。--text で文字も .txt で残す）
python -m yanua pdf-sort demo/company/paper/inbox --rules demo/company/paper/rules.json --out 仕分け済み --text

# 見本のPDFから、ルールの下書きを作る（--add-to でルールのファイルに足す）
python -m yanua pdf-rule-draft demo/company/paper/inbox/scan_0005.pdf --add-to demo/company/paper/rules.json

# Word / Excel に変換する
python -m yanua pdf-convert demo/company/paper/inbox/scan_0001.pdf --to docx
python -m yanua pdf-convert demo/company/paper/inbox/scan_0001.pdf --to xlsx

# 会社の様式に差し込む（ルールに様式があれば、その様式で作る）
python -m yanua pdf-convert demo/company/paper/inbox/scan_0001.pdf --to xlsx --rules demo/company/paper/rules.json
python -m yanua pdf-sort demo/company/paper/inbox --rules demo/company/paper/rules.json --out 仕分け済み --form
```

デモの仕分けの結果：

| 元のファイル | 置いた先 |
|---|---|
| scan_0001.pdf | 経理/請求書/2026/11/20261110_請求書_株式会社サンプル印刷_132000円.pdf |
| scan_0002.pdf | 総務/見積書/2026/20261105_見積書_有限会社テスト空調_385000円.pdf |
| scan_0003.pdf | 総務/議事録/2026/20261112_議事録_本社移転の定例会.pdf |
| scan_0004.pdf（画像だけ・OCR） | 総務/納品書/2026/11/20261113_納品書_合同会社ミホン事務用品_DN-5521.pdf |
| scan_0005.pdf（どのルールにも当たらない） | 未分類/scan_0005.pdf |

- **ルール**（JSON）は会社ごとに作ります。書類の種類を見分ける言葉（any / all / none）、ファイル名、保存先のフォルダを書きます。日付・金額・相手先の会社名は決まった形で読み取り、請求番号のような独自の項目は正規表現で足せます。書き方は `yanua/paper/rules.py` の説明を見てください。
- **ルールの選択**：当てはまるルールが複数あれば優先度と当たった言葉の数で選びます。`--rule` で指定もできます。どれにも当たらない書類は「未分類」へ置くか、`--use-llm` で社内のLLMにルール名の中から選ばせます（選択肢以外の答えは使いません）。
- **ルールの作成**：見本のPDFから下書きを作ります。`--use-llm` を付けると、見分けに使える言葉をLLMにも挙げさせます（書類の中に出てこない言葉は採りません）。下書きは確かめてから使います。
- **安全のため**：元のファイルは既定では残します（コピー）。同じ名前のファイルは上書きせず `_2` を付けます。読み取った項目にフォルダの区切りが入っていても、保存先の外には置きません。仕分けた結果は `_仕分け記録.csv` に残ります。
- **変換**：Word は1行1段落で本文を入れ、表は表として入れます。Excel は表を1つずつシートにし、表の外の文字は「本文」のシートに入れます。Excel の値は、数字も含めてすべて文字列で入れます（0 で始まるコードや郵便番号を崩さないため）。変換だけではレイアウトや図は再現しません。
- **様式への差し込み（フォームオーバーレイ）**：ルールに会社の様式（Word / Excel）を付けておくと、読み取った項目と明細を様式の決まった場所に入れて作ります。様式の罫線・文字の大きさ・セルの結合はそのまま残るので、「この様式を使ってください」と決めておけば形が崩れません。様式には `{{date_jp}}` `{{company}}` `{{amount_comma}}` のように差し込む位置を書き、明細は1行に `{{items.品目}}` のように書くと、PDFの表の行の数だけ増えます（合計・消費税の行は入れません）。スキャンしたPDFは、OCRの文字から明細の行を拾い、様式の列の順に入れます。どのルールにも当たらない書類と、様式のないルールの書類は、様式なしで変換します。書き方は `yanua/paper/form.py` の説明を見てください。

## 打ち合わせの記録

Web会議の録画（または録音）から、議事録の下書きを作ります。文字起こし・話し手の読み取り・要約は、すべてこの端末の中で行います。

```bash
# 文字起こしのモデルを入手する（1回だけ。許可リストの宛先から入手し、ハッシュを記録する）
python -m yanua models pull whisper-small
python -m yanua models list

# 議事録を作る（--tool は zoom / teams / meet / none）
python -m yanua meeting 録画.mp4 --title 本社移転の定例会 --tool zoom --date 2026-11-12 \
    --template demo/company/meeting/templates/議事録.docx --participants 本社5F会議室

# デモ（文字起こしの代わりに台本の発言を使う。話し手の読み取りと議事録づくりを確かめられる）
python -m yanua meeting demo/company/meeting/demo_zoom.mp4 --title 本社移転の定例会 \
    --segments demo/company/meeting/demo_zoom_segments.json --participants 本社5F会議室 \
    --template demo/company/meeting/templates/議事録.docx --date 2026-11-12
```

出力は `data/minutes/` に、議事録（Markdown・Word）と、時刻・話し手つきの発言の記録（JSON）を置きます。

- **文字起こし**：faster-whisper（ai-callcenter-ollama の `voice/stt_whisper.py` をもとに会議向けに広げたもの）。CPU・int8 で動き、無音の部分は飛ばします（VAD）。動画はそのまま入れられます（音声は PyAV で取り出してから渡します。faster-whisper 1.2.1 の取り出しが PyAV 19 で止まるため）。精度が足りなければ `models pull whisper-medium` で大きいモデルにします。
- **言葉のヒント**：会社の用語集（`--glossary`、1行に1語）・部署名・社員の名前（人事データから）を、文字起こしのヒントにします。社名や人名の聞き違いが減ります。
- **話し手**：声で人を聞き分けるのではなく、録画の画面に出ている名前を読みます。発言ごとに、その時刻の画面から、ギャラリービューでは発言中の強調の枠の中の名前を、スピーカービューでは画面の左下の名前を OCR で読みます。読んだ名前は人事データの氏名・出席者（`--participants`）と照らして表記をそろえます。1つの画面に複数人が映っていても、名前の表示が「本社5F会議室」なら、その名前を話し手にします。画面に出た名前（ログインした人の名前か、会議室のアカウント名）は、そのまま話し手と出席者に使います（出席者は確認の画面で直せます）。読めないときは「不明」です。Zoom・Teams・Meet の位置と色は `yanua/meeting/speakers.py` の `PRESETS` にあり、合わないときは `--debug-frames` で切り出した画像を見て直します。音声だけの録音には話し手を付けません。
- **要約**：社内のLLMで、要約・決まったこと・宿題（担当・内容・期限）を出します。長い会議は区切って読み取り、あとでまとめます。宿題の担当者は、会議に出てきた名前のときだけ残します（LLMが作った名前は「未定」）。小さなモデルは「決まったこと」や「私が〜します」の担当を落としやすいので、「〜で決定します」「〇〇さん、〜してください」「私が〜します」「次回は〜に開催します」といった決まった言い方は、発言から直接拾って補います（期限は担当者のその後の「〜までに」から取ります）。画面（API）の議事録の要約は、ほかの回答とは別のモデルを使います（`serve --summary-model`、既定 `qwen2.5:7b`。3b では要約・要点が空になりやすいため。デモの会議で 7b は約70秒）。要約が空になったときは、画面に「要約を作れませんでした。録画と照らして書いてください」と出し、理由（答えが JSON にならなかった など）はサーバーのログに残します。
- **議事録の様式**：紙の書類の差し込みと同じ書き方で、会社の議事録の様式（Word）に入れます。毎回「下書きなので出席者が確認すること」を入れます。
- **デモ動画**：`demo/company/meeting/demo_zoom.mp4` は、名前の表示と強調の枠だけを Zoom に似せた架空の画面で、声は入っていません。`make_demo.py --voicevox` で、この端末の VOICEVOX を使って声入りに作り直せます（声入りなら `--segments` なしで文字起こしから試せます）。

## 通信の方針

Yanua は、質問・資料・会議の中身を社外に送りません。そのうえで、更新やモデルの入手ができないと今の運用に合わないので、通信は「限定して、安全に」行います。どこへ・いつ通信するかは、管理者が画面「通信とモデル」（S-53）で決めて確かめます。決めたこと以外の通信はしません。

- **入口は1か所**：Yanua のコードが社外に通信するときは、必ず `yanua/net.py` を通します（Hugging Face のライブラリの通信も、同じ確かめを通します）。ON の宛先でなければ、つなぐ前に断ります。リダイレクト先も1件ずつ確かめます。通信は https だけで、証明書の検証は外しません。このマシンの中（手元の Ollama など）は社外ではないので、ここでは断りません
- **許可する宛先**：
  - 「既定」は `config/network.json` の `allowed_hosts`（今は Hugging Face）。一覧から消せません。画面で ON/OFF だけを切り替えられます
  - 「追加」は管理者が画面で足すもの。https のホスト名だけ（パス・ワイルドカード・IP アドレス・既定や追加との重複は不可）。足す・消す・ON/OFF ができます
  - 初めて入れたとき（起動したときに状態がないとき）は、既定の宛先をすべて ON で始めます（そのときの既定の宛先を `data/settings/network_known_defaults.json` に覚えます。版は増やしません）
  - 更新で既定の宛先が増えたら、新しいものは OFF で加え、画面の上に「新しい既定の宛先があります（宛先・用途）」と出します。ON にするかは管理者が決めます
  - 更新で既定の宛先が減ったら、その宛先には通信しません（画面に「既定から外れました」）
  - 画面で保存するのは、ON/OFF・追加の宛先・更新の確認の予定・入れ替えた版だけ（`data/settings/network_state.json`。版・既定に戻す・監査ログつき。説明は「huggingface.co を OFF」「registry.ollama.ai を追加」のように書きます）。「既定に戻す」は、既定の宛先をすべて ON にし、追加の宛先を消します（版は1つだけ増え、戻したあとは「既定」を使います。同じ操作の中で、今の既定の宛先を覚え直します）
- **いつ通信するか**：
  - 更新の確認は「しない」「手動だけ」（既定）「毎日」「毎週」から選びます（毎日・毎週は時刻も）。見に行くのは ON の宛先だけです。「しない」なら、時刻になっても、ボタンを押しても通信しません
  - 新しい版があっても自動では入れ替えません。画面に「新しい版があります」と出すだけです。入れ替えは、管理者が「入れ替える」を押したときだけ：入手 → 入手元のハッシュと照合 → 記録を更新、の順で、途中で失敗したら元のモデルのままです
  - モデルの入手（`models pull`）も、管理者が実行したときだけです。文字起こしや要約などのふだんの処理は、通信しない設定で動かします（ライブラリが勝手にダウンロードしないようにしています）
  - 見に行ったこと・入れ替えたこと・照合したことは、監査ログに残します（宛先・結果・版）
- **改ざんの防止**：
  - whisper（文字起こし）のモデルは、`config/network.json` の `revision` に、コミットのハッシュで版を固定します（`whisper-small` は、手元のファイルと Hugging Face のその版のファイルが一致することを確かめた版）。`revision` が空のモデルは入手しません（「版が固定されていません」）
  - 入手したファイルの SHA-256 を `data/models/models.lock.json` に記録します。`models verify` と使う前の照合は、記録した版が固定した版と同じかと、ファイルのハッシュの両方を確かめます。画面の「照合する」も同じで、通信しません
- **Ollama のモデル**：Ollama のモデルは、登録したときの digest を記録し、それとの一致を確かめる（入手元との照合は S-53 で足す）。
  - 目録（`config/network.json` の `models`）に `"kind": "ollama"` と用途（`use`：chat・summary・embedding）つきで載せたものだけを使います。今は `qwen2.5:3b-instruct` と `qwen2.5:7b`
  - 入手は `ollama pull <名前>` で行い、そのあと `python -m yanua models pull <名前>` で登録します。登録は手元の Ollama の digest（SHA-256）を `data/models/models.lock.json` に書くだけで、Yanua からは社外に通信しません
  - `python -m yanua models verify <名前>` と設定の画面（S-52）は、手元の Ollama の digest が登録したものと同じかを確かめます。違うとき（入れ替えた・すり替えられた）は使わせません。自分たちで入れ替えたと確かめたら `models pull <名前> --update` で登録し直します
  - 入手元（`registry.ollama.ai`）との照合は、S-53 で `registry.ollama.ai` を追加の宛先として足して ON にしたときだけ行います（既定では足しません）。そのときは「更新の確認」で入手元の digest と記録を比べ、違えば「入手元と違います」と出します。入れ替えは手で `ollama pull` → `models pull --update` です
- **network.json に誤りがあるとき**：起動は続けますが、社外にはどこにも通信しません（モデルの入手・更新の確認を止め、理由を画面に出します）
- **秘密の値**：Hugging Face のトークンが要るときは、環境変数 `HF_TOKEN` から読むだけです。画面にも記録にも出しません
- **会社側での強制**：アプリの中の制限は「うっかり」を防ぐためのものです。会社のファイアウォール・プロキシでも、同じ宛先だけを許可してください。モデルの入手には `huggingface.co` と `*.hf.co` が、ライブラリの更新（pip）には `pypi.org` と `files.pythonhosted.org` が要ります

## 画面で変えた設定

**画面で変えた設定は `data/settings/` にあり、リポジトリのファイルは既定です。**

- 画面から保存すると、その設定の中身の全部を写しとして `data/settings/` に書きます（例：仕分けルールは `data/settings/rules.json`）。リポジトリのファイル（例：`demo/company/paper/rules.json`）は書き換えません
- 読むときは、`data/settings/` に写しがあれば写しだけを使い、なければリポジトリの既定のファイルを使います
- 版の記録も `data/settings/history/<ファイル名>/` に残ります（`index.jsonl` と、版ごとの中身）。前の版に戻せます。「既定に戻す」は写しを消して既定を使います（消す前の写しは版として残ります）
- 画面で保存したあとに既定のファイルが更新されると（リポジトリを更新したときなど）、画面に「既定のルールが更新されています」と出ます。写しを使っている間は、既定の更新は入らないためです
- 保存の前に、その設定の読み込みと同じ検証をかけます。起動のときも、今使う設定を検証し、読み込めないところがあれば位置つきで出します（例：`rules[2].priority：優先度は整数にしてください`）
- **起動のときに設定に誤りがあったとき**：
  - 権限（初めての起動の `config/roles.json` と、DB の役割・グループ・割り当て）と本人確認の方針（`config/identity.json`）に誤りがあると、**起動しません**。だれが何をできるか、だれを本人と認めるかが決まらないまま動かさないためです。理由を出して止まるので、直してから起動し直してください
  - それ以外の設定（仕分けルールなど）に誤りがあると、誤りを位置つきで出して**起動は続けます**。止まるのは**その機能だけ**です（例：仕分けルールなら、PDF の仕分け・変換が直すまで使えません。ほかの機能は使えます）
- 置き場所は `serve --settings-dir` で変えられます。この仕組みは `yanua/settingfiles.py` の共通の部品です

**今、画面で変えられる設定**

| 設定 | 画面 | 既定のファイル | 画面で保存した写し |
|---|---|---|---|
| 仕分けルール | PDF の仕分け（S-20。総務） | `demo/company/paper/rules.json` | `data/settings/rules.json` |
| 本人確認の方針 | 設定（S-52。管理者） | `config/identity.json` | `data/settings/identity.json` |
| 監査ログ（保存期間・質問の本文を残すか） | 設定（S-52） | `config/audit.json` | `data/settings/audit.json` |
| モデル（チャット・議事録の要約） | 設定（S-52） | `config/models.json` | `data/settings/models.json` |
| ファイル（作業用フォルダの上限・消すまでの時間） | 設定（S-52） | `config/files.json` | `data/settings/files.json` |
| 人事（休職中の人のログインと権限） | 設定（S-52） | `config/hr.json` | `data/settings/hr.json` |
| 権限の条件と役職の段（管理の権限は確かな入口が要る・段の名前・「経営」に入る段） | 設定（S-52） | `config/access.json` | `data/settings/access.json` |
| 人事データの列の対応づけ（名前を付けて保存） | 人事データ（S-51。`hr.import`） | `config/hr_mappings.json` | `data/settings/hr_mappings.json` |

- 設定の画面（S-52）は管理者だけが使えます。どの設定も、保存した時から使われます（再起動は要りません）。写しを手で直したときなど、保存したものと動いている値が違うときは、画面の上に「再起動すると使われます」と出ます
- **起動の指定が勝ちます**：`serve --audit-body`・`--audit-keep-days`・`--model`・`--summary-model` を付けて起動すると、その項目は画面では変えられません（画面にそう出ます）。付けていない項目は、画面で保存したものを使います
- モデルは、目録（`config/network.json`）にあって、その用途（チャット・要約）のもので、`models pull` で登録した digest と手元の Ollama の digest が同じものだけを選べます。Ollama に入っていても目録にないモデルは出さず、API でも断ります。埋め込み用のモデルはチャット・要約の欄に出しません。目録にあっても入っていない・登録していない・digest が違うものは、理由を出して選ばせません
- **権限の条件と役職の段**：「管理の権限は確かな入口が要る」は、ON にすると管理の権限（権限を変える・設定・通信・監査ログ・受付端末の登録・人事データの取り込みと1つ前に戻す・文書の公開先と要る権限の変更）が SSO か多要素つきの Yanua アカウントで入ったときだけ効きます。今は入口が社員番号だけなので**既定は OFF** で、確かな入口で入っていない人は画面から ON にできません（SSO ができてから既定を ON にします）。ファイルで ON にして困ったときは、`data/settings/access.json` を直すか消して再起動します。「経営」に入る段を変えると、「経営」のグループの決まりがすぐ変わり、監査ログに `roles.group.update` で残ります
- 監査ログ・モデル・ファイル・人事・権限の条件の写しに誤りがあると、その設定だけ既定で動きます（起動は続けます。起動のときと画面に、直すところを出します）。本人確認の方針は、上のとおり誤りがあると起動しません。画面からは検証を通ったものしか保存できません
- 版の「したこと」と監査ログの説明には、変えた項目を短く書きます（例：「型 標準→社員コード必須」「チャットのモデル qwen2.5:3b-instruct→qwen2.5:7b」）。決まった項目だけを書き、長い文（最初の聞き方）は「変えた」とだけ書きます
- この画面では、秘密の値（トークン・パスワード・端末の値）は表示も保存もしません。役割と権限は「権限」の画面（S-54）、通信の許可リストは「通信とモデル」の画面（S-53）で変えます

## 権限の仕組み（職務ロール × 対象 × グループ）

考え方と、権限・役割の一覧は [docs/access-model.md](docs/access-model.md) にあります。

- **権限**は、できる操作の最小単位です。`yanua/permissions.py` に一覧があり、画面からは増やせません（33個：ふつうの権限27個と、作っておくだけの IaC の6個。2026-11-22 に roles.delegate・reports.view を足しました）
- **役割**は権限の束、**対象**は権限が効く先（部署・グループ・機能・システム・サーバー。特別な対象「メンバー自身の所属（部署と、入っているグループ）」「メンバー自身の部署」「全社」）、**グループ**は 役割 × 対象 を受け取る単位です。権限は人に直接は与えません。グループの入れ子は作りません
- **職務ロール**に、マネージャー・ディレクター（任せた管理と集計。既定ではどのグループにも与えない）と、経営（全社の文書と集計。管理の権限は入れない）があります。前の版のデータにも、起動のときに1回だけ足します
- **人の属性**（雇用区分・期限・役職・役職の段）は権限を持ちません。役職の段は「段が N 以上の人」の決まりで入るグループを通して効きます。既定の「経営」のグループは「段が役員（5）以上」で、役割「経営」× 全社 を持ちます（段の境目は設定 S-52 の「権限の条件と役職の段」）
- **条件**（入口・場所・端末）：判定は条件も受け取ります。今は入口が社員番号だけなので、既定の条件は「社員番号・社内・登録していない端末」です（`/api/me` の `context` に出ます）
- **メンバー**は、手で入れた人（期限つきにできる）と、グループの決まり（「全員」「この部署の人」「役職の段が N 以上の人」）で自動で入る人を、分けて持ちます。期限の切れたメンバーは、判定のときに数えません
- **判定は1か所**（`yanua/access.py` の `can`）：はい／いいえと、その理由（どのグループのどの役割から来たか）を返します。API の権限の確かめも、文書の検索の絞り込み（LLM に渡す前）も、これを使います。人ごとの結果は、変更があったときだけ作り直して持っておきます
- **置き場所**は社内文書と同じ SQLite（`data/index.db`）です。初めての起動で DB が空なら、`config/roles.json` から作ります（それ以後、roles.json は使いません）：
  - 「社員」（全員）× メンバー自身の所属（部署と、入っているグループ）、「総務」「人事」（部署の決まり）× 全社、前の「情シス」は「情シス・ヘルプデスク」（役割「ヘルプデスク担当」）× 全社
  - 「管理者」（roles.json の社員番号を、手で入れたメンバーにする）× 全社。今の動きを変えないため、「監査」（audit.view）と「文書管理」（前の documents.ingest）の役割も与えます
  - 「監査」のグループ（メンバーなし）。IaC の役割（インフラ技術者・承認者・実行者・管理）は作りますが、どのグループにも与えません
  - システムアカウント（受付端末・更新の確認）の種類も作っておきます（受付端末の端末トークンの移し替えは、まだ）
- **変える**のは「権限」の画面（S-54、`/admin/access`）です。見るのは `roles.view`、変えるのは `roles.assign` を持つ人だけです（どちらもない人にはメニューにも出しません）。タブは「グループ」「役割」「対象」「この人は何ができるか」の4つです
  - 変える前に、**だれのどの権限が増える・減るか**を出します（試しに当てるだけで保存しない API）。もう一度押すと保存します
  - その変更で**自分の権限が減る**ときは「外すと、あなた自身では戻せません。ほかの roles.assign を持つ人に頼むことになります」と出して、もう一度押してもらいます
  - 断られる変更は、理由を欄の近くに出します。画面専用の抜け道はなく、画面もほかと同じ API を使います
  - 対象のうち、部署（人事データから）・グループ・機能は自動でそろえます。システム・サーバーは手で作ります（つながる宛先は S-53 の宛先から選ぶ。接続情報は環境変数の名前だけを持ち、値は画面にもどこにも出しません）
- 変えるときの決まり：
  - **自分の権限が増える変更はできません**（自分のグループに役割や対象を足す・自分をグループに入れる・自分の期限を延ばす・自分のグループの役割に権限を足す）
  - 権限が減る変更と、自分に効かない変更はできます（例：全員が入る「社員」のグループから役割を外す）
  - **roles.assign を持つ人が1人もいなくなる変更はできません**（締め出しを防ぐ）
  - 決まり（全員・部署・役職の段）で入るグループは、メンバーを手で出し入れできません。roles.json で部署と社員番号の両方を書いた役割は、移し替えのときに「〇〇（個別）」のグループに分けます
  - グループはメンバーも役割もないときだけ、役割・対象・対象のまとまりはどこにも使っていないときだけ消せます
  - 変更は監査ログに中身つきで残します（例：「監査 に 山田 太郎 を追加（期限 2026-12-31）」）。断ったときも、理由つきで「拒否」として残します
- 権限の設定に誤りがあると、**起動しません**（権限と本人確認は止める、の決まりのまま）

### 管理者が自分の権限を外して戻せなくなったときの手順

画面と API では、roles.assign を持つ人が1人もいなくなる変更はできません。それでも、ただ1人の管理者が退職した・期限が切れた・自分の権限を外してしまったなどで、だれも権限を戻せなくなったときは、**サーバーに入れる人**が、サーバーの上でコマンドを使って戻します（画面からは使えません）。

```bash
# 1. 今の形を見る（グループ・役割・メンバー・割り当ての番号）
python -m yanua access show

# 2. 管理者のグループに人を入れる（グループと役割は、番号でも名前でもよい。期限は付けなくてもよい）
python -m yanua access add-member 管理者 10005
python -m yanua access add-member G-admin 10002 --expires 2026-12-31

# 3. 管理者の役割そのものを外してしまったときは、グループに 役割 × 対象 を与え直す
python -m yanua access add-grant 管理者 管理者 全社
```

- 別の場所の DB を使っているときは、`python -m yanua --db <パス> access ...` とします（監査ログが別の場所なら `access --audit-db <パス>`）
- 動いているサーバーは止めなくてかまいません。次の判定から効きます
- このコマンドには「自分の権限が増える変更はできない」の決まりを当てません（コマンドには「自分」がいないため）。ほかの決まり（決まりで入るグループには手で入れない・在籍している人だけ・同じ割り当ては足さない）は当てます
- 実行したことは**必ず監査ログに残します**（した人は「サーバーの操作」、名前に実行した OS ユーザー）。監査ログに書けないときは、何も変えません。うまくいかなかったときも「失敗」として残します
- 戻したあとは、画面（S-54）でほかの管理者を入れるなど、1人だけにならないようにしてください

**「管理の権限は確かな入口が要る」を ON にして、だれも管理できなくなったとき**：画面からは、確かな入口（SSO か多要素つきの Yanua アカウント）で入っていない人は ON にできません。それでもファイルで ON にしてしまい、確かな入口で入れる人がいないときは、サーバーに入れる人が次のようにして戻します。

1. `data/settings/access.json`（`serve --settings-dir` を変えたときはその中の `access.json`）を開き、`"admin_needs_strong_entry": true` を `false` に直す。写しをやめて既定（OFF）に戻すなら、ファイルを消してもよい
2. サーバーを再起動する（起動のときに読み直す）
3. 管理者で入り、設定の画面（S-52 の「権限の条件と役職の段」）で OFF になっていることを確かめる

## 監査ログ（何を記録し、何を残さないか）

だれが・いつ・何をしたかを、あとから確かめられるように記録します。管理者が画面「監査ログ」（S-55）で、期間・した人・操作の種類・結果で絞り込んで見られます。見たことも記録されます。

**記録するもの**（1件ごとに、時刻・した人（社員番号と名前。受付端末なら端末名。ログイン前は「なし」）・操作の名前・対象・結果（成功・失敗・拒否）・接続元の IP・短い説明）

- ログイン・ログアウト・ログインの失敗（開発用ログインも含む）
- 質問（チャット・ヘルプデスク）：だれが・いつ・どの画面で聞いたか、出典にした文書の番号と題名、答えたか断ったか（文書が見つからない・権限がない）。断ったときに、部署の権限で見せなかった文書があれば「権限がない」です。見せなかった文書は件数だけを残します（題名は残しません）。ヘルプデスクが決まった手順で案内したときは「手順で案内」です
- 権限が足りずに断った操作（403）。断った操作の名前も残します
- ジョブの開始・終わり・失敗・取り消し・中断（文書の取り込み・議事録・PDF の仕分けの予定・変換など）
- 受付端末の登録・取り消しと、コードを続けて間違えた端末の照合を止めたこと
- 設定の保存・版に戻す・既定に戻す（`data/settings/` の仕組みを通るものはすべて。今は仕分けルール）
- PDF の仕分けの実行（何件を、どのフォルダへ）
- ファイルのダウンロード（議事録の Word・変換の結果など。どのファイルを、だれが）

**残さないもの**

- パスワード・端末トークン・セッションのトークン・受付端末で入力されたコードは、どの設定でも残しません
- 質問の文、文書や PDF の中身は、既定では残しません。質問の文は `serve --audit-body` で起動したときだけ残します（既定は off）
- 部署の権限で見せなかった文書があることは、質問した人への返事には出しません（監査ログに件数だけ）
- 仕分けの実行では、書類の中身から作るファイル名（相手先・金額など）を残さず、フォルダだけを残します

**保管**

- 置き場所は `data/audit.db`（SQLite）。`serve --audit-db` で変えられます
- 記録は足すだけです。画面にも API にも、消す・書き換える操作はありません。データベースの中でも、書き換えと、保存期間の内の記録を消すことは断ります
- 保存期間は既定で 365日です（`serve --audit-keep-days`）。過ぎたものは、起動したときと1日1回まとめて消し、消したこと自体を1件記録します
- 記録に失敗しても、元の操作は止めません。サーバーのログにエラーを出します
- CSV への書き出しは、まだありません（設定の画面（K-042）と一緒に考えます）

## 依存ライブラリと、社外に通信できない環境への導入

依存ライブラリは版を固定し、CIで既知の脆弱性を検査しています。

- **Python**：`pip-audit -r requirements.txt`。指摘があれば CI を止めます
- **画面（web/）**：2段で検査します
  1. `npm audit --omit=dev`：配る画面に入るもの（`dependencies`。React など）だけを検査します。指摘があれば CI を止めます
  2. `npm audit`：組み立て・テストの道具（`devDependencies`。Vite・Vitest など）も含めた全部を検査します。指摘があっても CI は止めず、CI の画面に警告（⚠）を出します。道具は配る画面に入らず、利用者のパソコンでもサーバーでも動かないためです。警告が出たら、直った版が出しだい上げます

社外に通信できない環境には、通信できる環境でライブラリをまとめてダウンロードして持ち込みます。モデルも、通信できる環境で `models pull` したあと、`data/models/` ごと持ち込めば使えます（`models verify` で照合できます）。

```bash
# 通信できる環境で
pip download -r requirements.txt -d wheels
# 持ち込んだ先で
pip install --no-index --find-links wheels -r requirements.txt
```
