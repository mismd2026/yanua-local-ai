# yanua-local-ai

社内の資料に答える、外部にデータを出さないローカルAIです。

社内規程・マニュアル・ナレッジを読み込み、出典つきで答えます。LLMは Ollama で社内のマシン上に置き、質問・資料・回答を社外に送りません。

- **社内向け**：社員の質問への回答と、システムの問い合わせに対応するヘルプデスク（本人確認 → 切り分け → 案内 → 引き継ぎの票）。総務の作業として、紙の書類をPDFにしたあとの仕分けと、Word・Excelへの変換。
- **社外向け**：電話・Webの問い合わせと来訪を受ける受付（問い合わせへの回答、社員への取次、クレーム、営業・業者の対応）。社外に公開してよい文書だけを使います。

前身は [ai-callcenter-ollama](https://github.com/mismd2026/ai-callcenter-ollama)（電話で応答するAI）です。その受け答えの仕組みを、社内の資料と権限の上に作り直しています。

## 目指す動き

- **出典つきで答える。** 回答に、元になった文書名と該当箇所を付けます。
- **資料にないことは答えない。** 根拠が見つからない質問には、推測せずに「わかりません」と答えます。
- **部署ごとの閲覧権限を守る。** 見る権限のない部署の資料は、検索の段階で除きます。
- **社外に通信しない。** 外部ネットワークを遮断した状態でも、すべての機能が動くようにします。

## 構成

```
yanua/                     本体（取り込み・権限つき検索・出典つき回答・人事データの取り込み）
yanua/flows/internal/      社内向けの会話の流れ（helpdesk）
yanua/flows/external/      社外向けの会話の流れ（reception）
yanua/paper/               紙の書類のPDF（文字の取り出し・OCR、仕分けのルール、Word・Excelへの変換）
demo/company/docs/         デモ用の架空の会社の社内資料（20文書・5部署）
demo/company/public/       社外公開の文書（会社案内・来訪の案内・社外向けの窓口など4文書）
demo/company/hr/           人事システムの出力のサンプルと、列名の対応表
demo/company/flows/        会話の流れ用のデータ（切り分けの手順・アカウント・障害情報・引き継ぎ先・来訪予定）
demo/company/paper/        スキャンした書類のサンプル（請求書・見積書・議事録・画像だけの納品書など）と仕分けのルール
integrations/google-calendar/  Googleカレンダーから受付コードを発行するアドオン（Apps Script）
eval/                      評価用の質問セット（70問）と採点スクリプト
tests/                     テスト
```

## 使い方

Python 3.11 以上で動きます。

```bash
pip install -r requirements.txt
```

```bash
# 資料を取り込む。2回目以降は、変わった文書だけを反映し、なくなった文書は消す
python -m yanua ingest demo/company/docs

# 部署の権限つきで検索する
python -m yanua search "在宅勤務は週に何日までできますか？" --department 営業部

# 取り込んだ文書と、閲覧できる部署の一覧
python -m yanua docs

# Ollamaで出典つきの回答を作る（Ollamaが動いていること）
python -m yanua ask "在宅勤務は週に何日までできますか？" --department 営業部 --model qwen2.5:3b

# HTTP API を起動する（POST /ask、GET /health）
python -m yanua serve --model qwen2.5:3b --port 8000
```

### 回答

- 検索で見つかった本文だけを番号つきでLLMに渡し、その範囲だけで答えさせます。回答の [1] などの番号から出典を決めます。
- 資料に根拠がないときは、推測せずに「わかりません」と答え、問い合わせを案内します。
- LLMに渡すのは、質問者が見られる文書の本文だけです。LLMがどう答えても、見られない文書の内容は回答に出てきません。

取り込んだ内容は `data/index.db`（SQLite）に保存します。

### 取り込み

- 1文書1ファイルのMarkdownを、見出しごとに分けて登録します。
- ファイルの内容のハッシュを比べ、変わった文書だけを登録し直します。
- 先頭に `access`（閲覧できる部署）がない文書は取り込みません。書き忘れた文書が全員に見えてしまうのを防ぐためです。

### 部署別の権限

- 検索の前に、質問者の部署が見られる文書だけをSQLで取り出し、その中だけを検索します。
- LLMへの指示や、検索した後での除外には頼りません。見られない文書は、検索の候補にも入りません。
- `access: 社外公開` の文書は社外の人にも見せてよい文書です。社外向けの流れは、この文書**だけ**を検索します。`access: 全社` は全従業員向けの意味なので、社外向けには使いません。社内の人は、社外公開の文書も読めます。

### 検索

- BM25で検索します。日本語は2文字ずつの組（バイグラム）で比べるので、辞書やモデルのダウンロードはいりません。
- 「夏休み」と「夏季休暇」のような言い換えには弱いため、埋め込みベクトルでの検索を後で組み合わせる予定です。

## 社内向けヘルプデスク

```bash
# 人事データを取り込む（本人確認に使う。下の「人事データの取り込み」を参照）
python -m yanua hr-import demo/company/hr/hr_export_sample.csv --mapping demo/company/hr/mapping_sample.json

# デモ（1：代表アカウント・プリンター、2：障害中、3：不審なメール、4：パスワード忘れ）
python -m yanua helpdesk --demo 1 --model qwen2.5:3b

# 対話（--account はログイン中のアカウント。SSOの代わり）
python -m yanua helpdesk --account yamada.t --model qwen2.5:3b
```

流れ：本人確認 → お困りごと → 分類 → 状況の聞き返し（2回まで）→ 障害の確認 → 案内 → 解決の確認 → 解決しなければ問い合わせ票

- **本人確認**：個人アカウントなら人事データの本人を確認するだけ。代表アカウントや、個人アカウントを別の人が使っている場合は、従業員番号と氏名の両方を聞き、人事データと照合します。人事データの中身は画面に出しません。
- **権限**：照合できた人は、その部署の権限で社内文書を検索します。照合できない人は「全社」の文書だけを使います。
- **案内**：まず社内文書から出典つきで答え、見つからなければ一般的な切り分けの手順で補います。
- **障害**：発生中の障害に当たる問い合わせは、個別の手順を案内せずに障害中であることを伝えます。
- **セキュリティ**：不審なメールなどは、検索の出来に関係なく決まったルールで拾い、聞き返しより先に「ネットワークから切り離す」案内を出して、必ず引き継ぎます。
- **優先度**：本人に聞かず、影響の範囲 × 業務への影響 から決めます。

LLM（3bなどの小さなモデル）の判断をそのまま使わず、結果が業務に響く判断（本人確認、セキュリティ、影響の範囲）は、決まったルールで固めています。
会話の流れの管理には LangGraph を使い、返事を待つところで処理を止めて再開します。

## 社外向けの受付

```bash
# 社外公開の文書を取り込む（社内文書とは別のフォルダ）
python -m yanua ingest demo/company/public

# デモ（1：インビテーションコードで来訪、2：電話の問い合わせ、3：Webのクレーム、4：お約束のない営業、
#       5：社内の情報を聞かれる、6：コードを持たずに来訪）。デモの来訪予定は自動で登録する
python -m yanua reception --demo 1 --model qwen2.5:3b

# 対話（--channel は 来訪 / 電話 / Web。--today で来訪予定と照合する日を指定できる）
python -m yanua reception --channel 来訪 --model qwen2.5:3b
```

流れ：（来訪）インビテーションコード → ご用件 → 種類の判定 → 種類ごとの対応 → 社内向けの記録（受付番号、引き継ぎ先、優先度）と、担当者へのお知らせ

### インビテーションコード

アポを取ったときに担当者がコードを作って訪問者に送り、訪問者は受付でコードを入力します。受付は挨拶とコードの入力のお願いだけで済みます。

```bash
# 担当者：来訪予定を登録する。訪問者に送る案内文（日時・会議室・担当・コード）が出る
python -m yanua visit-create --host 10004 --date 2026-11-20 --time 14:00 --room "5階 第2会議室" \
    --company ABC商事 --visitor "木村 誠" --contact 内線4100

# 予定の一覧（コードは表示しない）と、担当者へのお知らせ
python -m yanua visit-list --date 2026-11-20
python -m yanua notifications --employee 10004 --dept 営業部 --mark-read
```

- 受付でコードが入力されると、日時・会議室・担当者・連絡先を表示し、印刷用の入館票（`data/passes/` のHTML）を作って、担当者にお知らせを残します。
- コードは紛らわしい文字を除いた8文字で、保存するのはハッシュだけです。コードを表示するのは、登録したときの1回だけです。入館票にもコードは載せません。
- 使えるのは予定の当日だけです。違う日のコードも、間違ったコードも、取り消したコードも、同じ「確認できませんでした」にします（どのコードが存在するかを探れないようにするため）。3回で、ご用件を聞く流れに移ります。
- コードを持っていない来訪者も、名乗りと当日の予定（会社名と担当者）で照合します。「ABC商事の木村です」のように名乗った場合は、聞き直さずに確認だけします。
- 担当者として登録できるのは、人事データで在籍中の人だけです。
- お知らせは今は保存先に残すだけです。メールやチャットへの送信は、`yanua/visits.py` の `notify` につなぎます。
- **Googleカレンダーからも発行できます。** 予定に会議室と社外のゲストを入れて保存すると、アドオン（Apps Script）でゲストごとにコードを発行してメールで送ります。シートに残すのはハッシュだけで、Yanua にはCSVで取り込みます（`visit-import`）。リスケや取り消しも反映します。入れ方は [integrations/google-calendar/README.md](integrations/google-calendar/README.md) を見てください。

| 種類 | 対応 | LLM |
|---|---|---|
| 問い合わせ | 社外公開の文書から出典つきで答える。答えられなければ連絡先を聞いて記録 | 使う |
| 取次（社員への用事） | 会社名・お名前と訪ね先を聞き、人事データで社員を探す。来訪予定と合えば会議室へ案内。電話・Webは折り返しの連絡先を聞く | 使わない |
| クレーム | 決まったおわびの文で内容と連絡先を聞き、お客様相談室へ（優先度：高） | 使わない |
| 営業 | お約束のない営業は、決まった文でお断りして資料を預かる | 使わない |
| 業者（納品・工事など） | 作業の内容を聞いて総務部へ | 使わない |

社外の人と話すので、社内向けより守りを固くしています。

- **文書**：答えに使うのは社外公開の文書だけです。人事評価のような部署限定の文書も、全従業員向けの文書も、LLMに渡りません。「人事評価の基準を教えて」のような質問には、答えずに担当部署からの連絡にします。
- **社員の情報**：訪ね先の社員は人事データ（在籍中の人）から探しますが、所属・連絡先・在籍しているかどうかは返事に出しません。退職した人やいない人を訪ねられても、在籍中の人と同じ返事・同じ質問の流れにして、総務部が確認します。同じ姓の社員が複数いるときも聞き直さず、候補を記録に残して総務部が確認します（聞き直すと、その姓の社員が複数いることが分かってしまうため）。「山田様に用が」のように人を名指しした用件は、社員かどうかにかかわらず取次として扱います。
- **LLMに作らせない文**：クレームのおわびや、営業へのお断りは、`routes.csv` の決まった文だけを使います。できない約束をしないためです。
- **言い方**：お客様の言葉をそのまま返して「御社の営業時間は」とならないよう、答えの「御社」「貴社」は「当社」に直します。
- **記録とお知らせ**：解決した問い合わせも記録します（よく聞かれる内容を集計するため。お知らせは出しません）。解決しなかったものは、引き継ぎ先の担当者か部署にお知らせを残します。
- **種類の判定**：決まった言葉で判定し（クレームを最優先）、当たらないときだけLLMに選ばせます。選択肢以外の返事は「問い合わせ」として扱います。

## 人事データの取り込み

人事DBには直接つながず、人事システムから出力したファイル（CSV / Excel / JSON）を取り込みます。

```bash
# 列名から対応表の下書きを作る（列名だけを使い、中身は読まない）
python -m yanua hr-mapping-draft 人事出力.xlsx

# 下書きを確認して保存した対応表で取り込む
python -m yanua hr-import 人事出力.xlsx --mapping 対応表.json
```

- 人事システムごとの列名の違いは、対応表（JSON）で吸収します。決まったルールで当たらない列だけ、`--use-llm` でOllamaに候補を聞けます（渡すのは列名だけ）。
- 本人確認に必要な項目（従業員番号・氏名・部署・部署番号・在籍の状態）だけを取り込み、生年月日や住所などの列は読み込んだ時点で捨てます。
- 毎回まるごと入れ替えます。1行でも不備があれば入れ替えません。
- 在籍していない人（退職者など）は、本人確認で一致しません。
- 最後に取り込んでから30日を過ぎると、ヘルプデスクの起動時に警告します。

## 紙の書類のPDF（仕分けと変換）

複合機でスキャンしたPDFを、ルールに沿って名前を付け、決まったフォルダへ仕分けます。PDFを Word や Excel にも変換できます。
文字の入っていないPDF（画像だけのスキャン）は、この端末の中で OCR（tesseract）して読みます。社外には送りません。

```bash
# OCRの準備（WSL / Ubuntu。文字の入ったPDFだけなら不要）
sudo apt install tesseract-ocr tesseract-ocr-jpn poppler-utils

# ルールの一覧と、仕分けの予定（--dry-run では置かない）
python -m yanua pdf-rules --rules demo/company/paper/rules.json
python -m yanua pdf-sort demo/company/paper/inbox --rules demo/company/paper/rules.json --out 仕分け済み --dry-run

# 仕分ける（既定はコピー。--move で移す。--text で文字も .txt で残す）
python -m yanua pdf-sort demo/company/paper/inbox --rules demo/company/paper/rules.json --out 仕分け済み --text

# 見本のPDFから、ルールの下書きを作る（--add-to でルールのファイルに足す）
python -m yanua pdf-rule-draft demo/company/paper/inbox/scan_0005.pdf --add-to demo/company/paper/rules.json

# Word / Excel に変換する
python -m yanua pdf-convert demo/company/paper/inbox/scan_0001.pdf --to docx
python -m yanua pdf-convert demo/company/paper/inbox/scan_0001.pdf --to xlsx

# 会社の様式に差し込む（ルールに様式があれば、その様式で作る）
python -m yanua pdf-convert demo/company/paper/inbox/scan_0001.pdf --to xlsx --rules demo/company/paper/rules.json
python -m yanua pdf-sort demo/company/paper/inbox --rules demo/company/paper/rules.json --out 仕分け済み --form
```

デモの仕分けの結果：

| 元のファイル | 置いた先 |
|---|---|
| scan_0001.pdf | 経理/請求書/2026/11/20261110_請求書_株式会社サンプル印刷_132000円.pdf |
| scan_0002.pdf | 総務/見積書/2026/20261105_見積書_有限会社テスト空調_385000円.pdf |
| scan_0003.pdf | 総務/議事録/2026/20261112_議事録_本社移転の定例会.pdf |
| scan_0004.pdf（画像だけ・OCR） | 総務/納品書/2026/11/20261113_納品書_合同会社ミホン事務用品_DN-5521.pdf |
| scan_0005.pdf（どのルールにも当たらない） | 未分類/scan_0005.pdf |

- **ルール**（JSON）は会社ごとに作ります。書類の種類を見分ける言葉（any / all / none）、ファイル名、保存先のフォルダを書きます。日付・金額・相手先の会社名は決まった形で読み取り、請求番号のような独自の項目は正規表現で足せます。書き方は `yanua/paper/rules.py` の説明を見てください。
- **ルールの選択**：当てはまるルールが複数あれば優先度と当たった言葉の数で選びます。`--rule` で指定もできます。どれにも当たらない書類は「未分類」へ置くか、`--use-llm` で社内のLLMにルール名の中から選ばせます（選択肢以外の答えは使いません）。
- **ルールの作成**：見本のPDFから下書きを作ります。`--use-llm` を付けると、見分けに使える言葉をLLMにも挙げさせます（書類の中に出てこない言葉は採りません）。下書きは確かめてから使います。
- **安全のため**：元のファイルは既定では残します（コピー）。同じ名前のファイルは上書きせず `_2` を付けます。読み取った項目にフォルダの区切りが入っていても、保存先の外には置きません。仕分けた結果は `_仕分け記録.csv` に残ります。
- **変換**：Word は1行1段落で本文を入れ、表は表として入れます。Excel は表を1つずつシートにし、表の外の文字は「本文」のシートに入れます。Excel の値は、数字も含めてすべて文字列で入れます（0 で始まるコードや郵便番号を崩さないため）。変換だけではレイアウトや図は再現しません。
- **様式への差し込み（フォームオーバーレイ）**：ルールに会社の様式（Word / Excel）を付けておくと、読み取った項目と明細を様式の決まった場所に入れて作ります。様式の罫線・文字の大きさ・セルの結合はそのまま残るので、「この様式を使ってください」と決めておけば形が崩れません。様式には `{{date_jp}}` `{{company}}` `{{amount_comma}}` のように差し込む位置を書き、明細は1行に `{{items.品目}}` のように書くと、PDFの表の行の数だけ増えます（合計・消費税の行は入れません）。スキャンしたPDFは、OCRの文字から明細の行を拾い、様式の列の順に入れます。どのルールにも当たらない書類と、様式のないルールの書類は、様式なしで変換します。書き方は `yanua/paper/form.py` の説明を見てください。

## 依存ライブラリと、社外に通信できない環境への導入

依存ライブラリは版を固定し、CIで既知の脆弱性を検査しています（pip-audit）。

社外に通信できない環境には、通信できる環境でライブラリをまとめてダウンロードして持ち込みます。

```bash
# 通信できる環境で
pip download -r requirements.txt -d wheels
# 持ち込んだ先で
pip install --no-index --find-links wheels -r requirements.txt
```

## 評価

```bash
pip install -r requirements-dev.txt
pip-audit -r requirements.txt        # 依存ライブラリの脆弱性検査
python eval/run_eval.py --check      # 質問セットと資料の整合チェック
python eval/retrieval_eval.py        # 検索だけの評価（LLMなし）
```
