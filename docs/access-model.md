# 権限の仕組み（職務ロール × 対象 × グループ、人の属性、条件）

2026-11-22 に決めたこと（下の 1〜10）に合わせて書き直した。**この版で作ったのは「考え方・データの土台」まで**で、SSO などの入口はまだない（K-008・K-060〜）。表の「今」の列で、作ったもの・まだのものを分けて書く。

## なぜ変えるか
今は部署と役割（config/roles.json の5つ）で決めているが、同じ部署の中にも特権を持つ人とそうでない人がいる。また、部署をまたぐグループに専用で公開したいものがある。将来は IaC（クラウドの構成を読み取り・変更する機能）など、どのシステム・サーバーに接続してよいかを決める権限も要る。
さらに、社員のほかに契約・派遣・外部委託の人がいる、役職（課長・役員など）で見られるものが変わる、マネージャーに管理の一部を任せたい、社外から使いたい、という求めがある。これらを「権限を増やす」のではなく、**権限は職務ロール × 対象だけで決め、人の属性（雇用区分・役職）と条件（入口・場所・端末）は、その外から効かせる**形にする。

## 決まったこと（2026-11-22）
1. 権限は「**職務ロール × 対象**」で決める（今のまま）。職務ロールに「マネージャー」「ディレクター」「経営」を足す。経営は全社の文書と集計を見る。管理の権限（roles.assign・設定・監査の設定）は含めない。
2. **雇用区分**（社員・契約・派遣・短期・外部委託）は人の属性。権限は持たない。使い道は (a) 期限（契約の終わりの日）、(b) 会社が決める「この区分では持てない権限」の一覧（既定は空）、(c) 画面での表示 の3つだけ。
3. **役職**も人の属性。権限は持たない。「役職」（名前は会社ごと）と「役職の段」（比べるための数。例：1＝一般 … 6＝社長）を持つ。「段が N 以上の人はグループ X に入る」という決まりで入るグループを作れる（部署の決まりと同じ作り）。既定では「経営」のロールを「段が役員以上の人」のグループに与える。
4. **マネージャーに任せる管理**：自分の対象の範囲で、人をグループに期限つきで足す・外す。「この人と同じ範囲を期限つきで」も含める。渡せるのは自分が持っている権限まで。秘書・代理に「同じ範囲を期限つきで」を使うとき、経営向けの文書まで渡せるかは決まりで選べる（既定は渡さない）。
5. **見られる範囲は仕事（部署・グループ）で決める**。アカウントの有無では決めない。文書はコピーせず、公開先（部署・グループ）で共有する。ファイルごとに人へ権限を付ける形は作らない。
6. **入口は3つ**：SSO、Yanua のアカウント（期限・多要素つき。アカウントのない人や、管理を任せる派遣・契約の人に使う）、登録した共有端末＋社員番号。
7. 権限の判断に**条件**を足す：どの入口で入ったか・どこからか（社内・社外）・どの端末か（登録した端末か）。管理の権限は確かな入口（SSO か多要素つきの Yanua アカウント）で入ったときだけ有効。文書に「確かな入口が要る」「社外からは見せない」の印を付けられる。社外から入れるのは SSO と多要素つきのアカウントだけ。共有端末の入口は社内だけ。監査ログに入口と場所を残す。
8. **人の台帳**：人事データと派遣・委託の台帳を1つにまとめる（持つ項目・持たない項目は下の表）。
9. **照合**：人事データ・台帳・IdP の情報を突き合わせ、食い違いを一覧と CSV に出す。Yanua から AD・Entra ID へは書き込まない。書き戻しは最後の段階で検討し、そのときは「試し → 承認 → 実行」の門を通す。
10. **Yanua の範囲**：人事・情報システム寄りの土台にする。売上の仕組みは Yanua に入れず、別のシステムにする（未来のマイルストーン）。

## 要素
| 要素 | 中身 |
| --- | --- |
| 権限 | できる操作の最小単位。コード（yanua/permissions.py）で決める。画面からは増やせない |
| 職務ロール（役割） | 権限の束。データとして持つ |
| 対象 | 権限が効く先。種類は 部署・グループ・機能・システム・サーバー。まとめて名前を付けられる（対象のまとまり）。特別な対象は3つ（下の表） |
| グループ | 職務ロール × 対象 を受け取る単位。権限は人に直接は与えない。入れ子は作らない。入り方は「手で入れる」か決まり（全員・部署・役職の段） |
| アカウント | グループのメンバー。人とシステムの2種類。メンバーには期限を付けられる |
| 人の属性 | 人の台帳の項目（部署・在籍状態・雇用区分・期限・役職・役職の段など）。属性そのものは権限を持たない。部署と役職の段は、決まりで入るグループを通して効く |
| 条件 | どの入口で入ったか・どこからか・どの端末か。権限を「足す」ことはなく、決まりに当たる権限を「効かせない」だけ |
| 文書・データ | 持ち主の部署・公開先（部署・グループ・全社から1つ以上）・見るのに要る権限（既定 documents.view。文書向けの権限 infra.docs.view も選べる）を持つ（S-50）。見られるのは、要る権限を公開先を含む対象で持っているときだけ。公開先「全社」はどの対象にも含まれる。社外公開は社外向けの受付だけが使う印（社内での見え方は公開先で決める）。条件の印（下の「条件」）も付けられるようにする |

判定：その対象に対して、要る権限を持つグループに入っていて、条件で止められていないときだけ、見られる・できる。判定は `Engine.can(アカウント, 部署, 権限, 対象, 条件)` の1か所。

### 特別な対象
| 対象 | 番号 | 含むもの |
| --- | --- | --- |
| メンバー自身の所属（部署と、入っているグループ） | special:self | その人の部署と、その人が今入っているグループ（決まりで入るもの・手で入れたもの。期限の切れたものは含まない）。人ごとに中身が変わる。役割「社員」の既定の対象 |
| メンバー自身の部署 | special:self_dept | その人の部署だけ（グループは含まない）。前の版での「社員」の対象。今も選べる。マネージャーに与えるときの既定の対象 |
| 全社 | special:all | すべての部署・グループ。文書の公開先「全社」は、どの対象にも含まれる |

例：文書 H01 の公開先を「グループ：総務」にすると、社員（documents.view × メンバー自身の所属）のうち、総務のグループに入っている人だけが見られる。
前の版のデータ（「社員」× メンバー自身の部署）は、起動のときに1回だけ、自動で「社員」× メンバー自身の所属 に置き換える（監査ログに「roles.migrate」で残す）。そのあと画面で「メンバー自身の部署」に戻したら、戻したままにする。

## 人の属性：雇用区分と役職
### 雇用区分
| 区分 | 例 |
| --- | --- |
| 社員 | 正社員・常勤 |
| 契約 | 契約社員・嘱託 |
| 派遣 | 派遣社員 |
| 短期 | アルバイト・パート・インターン |
| 外部委託 | 業務委託・協力会社 |

- 権限は持たない。使い道は次の3つだけ：
  - (a) **期限**（契約の終わりの日）：人の台帳の「期限」。期限が過ぎた人に権限が残っていないかは照合（K-064）で出す。期限で自動でログインを止めるかは、Yanua のアカウント（K-061）と一緒に決める（今は止めない）
  - (b) **この区分では持てない権限**の一覧：会社が決める（既定は空）。例「派遣は hr.view を持てない」。グループに入っていても、その権限だけ効かせない（条件と同じく「足す」ことはない）。今は一覧の置き場所だけ決め、判定には入れていない（K-062）
  - (c) **画面での表示**：一覧や「この人は何ができるか」に区分を出す
- 人事データの取り込み（S-51）で列を割り当てる。ファイルの値（例「正社員」「契約社員」「業務委託」）は、在籍状態と同じ作りで5つの区分に対応づける（`employment_values`）。対応づけていない値は誤り（行番号つき）
- 列を「使わない」にしたら、今いる人は今の値のまま、新しく入る人は「社員」。この版より前からいる人は「社員」・期限なし・役職は空

### 役職と役職の段
- 「役職」は名前（会社ごと。例「課長」「本部長」）。「役職の段」は比べるための数（1〜99）。段の名前は設定で決める（既定：1 一般・2 主任・3 課長・4 部長・5 役員・6 社長）
- どちらも権限は持たない。**段で決まるグループ**（決まり `{"min_level": N}`：在籍している人のうち、段が N 以上の人）を通して効く。部署の決まりと同じ作りで、メンバーは手で出し入れしない。昇格して段が N 以上になれば入り、退任して下がれば外れる（取り込みの試しの「権限への効き方」に、グループごとの人数で出る）
- 段が空の人は、段の決まりのグループには入らない
- 人事データの取り込みで「役職」「役職の段」の列を割り当てる（段は整数。読めない値は誤り）

## 任せた管理（マネージャー・ディレクター）
| 決まり | 中身 |
| --- | --- |
| できること | 自分の roles.delegate の対象（例：メンバー自身の部署）の範囲で、人をグループに**期限つきで**足す・外す。期限なしにはできない |
| 同じ範囲を期限つきで | 「この人と同じ範囲を期限つきで」：ある人が入っているグループ（手で入れたもの）に、別の人を同じ期限で足す。代理・引き継ぎに使う |
| 渡せるもの | 自分が持っている権限まで。足す先のグループの権限が、自分の持つ権限（対象を含む）を超えるときは断る |
| 秘書・代理 | 「同じ範囲を期限つきで」で経営の人と同じ範囲を渡すとき、経営向けの文書（公開先が経営のグループ・「確かな入口が要る」の印）まで渡すかは決まりで選ぶ。**既定は渡さない**（経営のグループは写さない） |
| 渡せないもの | 管理の権限（roles.assign・設定・監査など）、決まりで入るグループ（全員・部署・役職の段）のメンバー、自分自身 |
| 記録 | 足した・外したことは、監査ログに中身つきで残す（任せた人・任された人・期限） |
| 今 | 権限 roles.delegate と役割だけ。動き（画面と API）は K-063 |

## 照合と書き戻し
- 照合（K-064）：人事データ・人の台帳・IdP（SSO の情報）を突き合わせ、食い違いを一覧と CSV に出す。例：退職したのに IdP のアカウントが残っている、人事データと IdP で部署が違う、期限が切れたのに権限が残っている
- Yanua から AD・Entra ID へは書き込まない（読むだけ）
- 書き戻し（K-066）は最後の段階で検討する。そのときは IaC と同じく「試し → 承認 → 実行」の門を通す形にし、承認と実行は別の人にする

## Yanua の範囲
Yanua は人事・情報システム寄りの土台（人の台帳・アクセスモデル・監査ログ・通信の決まり・ローカルの Qwen）。売上の仕組み（商材 × 販路 × 拠点 × 期間の集計と見込み。K-068）は Yanua に入れず別のシステムにし、この土台を共有する前提にする。

## 決まり
- システムアカウントは画面にログインしない（鍵やトークンで API だけ）。
- 権限を変えられるのは roles.assign を持つ人だけ。変更はすべて監査ログに中身つきで残す（断ったときも「拒否」で残す）。
- 自分の権限が増える変更はできない：自分が入っているグループに役割や対象を足す、自分をグループに入れる、自分の期限を延ばす（期限なしにするのも含む）、自分のグループが使っている役割に権限を足す。
- 権限が減る変更と、自分に効かない変更はできる（例：全員が入る「社員」のグループから役割を外す、ほかのグループを変える）。
- roles.assign を持つ人が1人もいなくなる変更はできない（締め出しを防ぐ）。同じ考え方で、確かな入口で入っていない人は「管理の権限は確かな入口が要る」を ON にできない。
- 決まり（全員・部署・役職の段）で入るグループは、メンバーを手で出し入れできない。中身（役割・対象）は上の決まりの範囲で変えられる。決まりの人に加えて個別の人も入れたいときは、別のグループ（例「総務（個別）」）にする。
- 期限が来たメンバーは自動で外れる。
- **在籍の状態**（人事データ。在籍・休職・退職。S-51 で取り込む。K-054）：
  - 退職した人はログインできない。決まり（全員・部署・役職の段）で入るグループにも、手で入れたグループにも数えない（判定で除く）。取り込みで退職になった人・人事データからいなくなった人は、手で入れたグループのメンバーから外し、監査ログに残す（`roles.member.remove`）。復職・再入社で在籍に戻っても、手で入れたグループのメンバーは自動では戻さない（手で入れ直す）
  - 休職中の人は、設定（S-52 の「人事」）で決める：ログインできる・できない、権限「そのまま」か「社員の役割だけ」（役割「社員」から来る権限だけが効き、ほかのグループの役割は効かない）。既定は今のまま（ログインできる・権限そのまま）
  - 部署や役職の段が変わると、決まりで入るグループが入れ替わる（取り込みのあと、判定の結果を作り直す）
  - 人事データの取り込みで roles.assign を持つ人がいなくなるときは、確定しない（締め出しを防ぐ）
- それでもだれも権限を戻せなくなったときは、サーバーに入れる人が復旧用のコマンド（python -m yanua access）で戻す。コマンドには「自分」がいないので自分の権限の決まりは当てないが、実行したことは必ず監査ログに残す（した人は「サーバーの操作」と OS ユーザー）。「管理の権限は確かな入口が要る」を ON にして困ったときは、保存した設定（data/settings/access.json）を直すか消して再起動する。
- SSO（K-008）では、IdP のグループを Yanua の「IdP で入るグループ」に結び付ける。部署は IdP ではなく人事データから決める。
- 接続情報（鍵）は対象の側に参照名として置き、グループや人には渡さない（IaC のとき）。
